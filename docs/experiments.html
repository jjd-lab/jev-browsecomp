100 questions · 1,000 documents each

Jev picks the documents. One call answers.

On BrowseComp-Plus, the Jev screen picks 8 of 1,000 documents and one Sonnet 5 call answers from them. This Jev reader matches the accuracy of a Sonnet 5 Recursive Language Model, or RLM, at $0.13 per question instead of $0.35, and 21 seconds instead of 143.

The three methods

Every question comes with 1,000 BrowseComp-Plus documents, about 7 to 9 million tokens. A few of them hold the answer and the facts behind its clues; the rest are random. A Sonnet 5 judge marks each answer right or wrong against the benchmark's answer. We call one method better only when the 95% confidence interval for the difference, over the same questions, is entirely above or below zero.

Jev is used in two ways. Take a made-up question: which painter failed an art school's entrance exam and later taught there?

  • Jev screen scores each document for how likely it is to help answer the question. A biography of a painter who taught at an art school might score 0.9, and a football match report 0.01.
  • Jev decide reads up to 8 documents and says whether they are enough to answer (act), need a closer look (review), or are not enough (abstain), and which of them to cite.
Plain RLM

Sonnet searches with code.

Sonnet 5 gets the documents in a Python session, writes code to search them, and hands pieces to Haiku 4.5 to read. It stops when it answers or runs out of turns. It never calls Jev.

The Jev reader scored 3 points above the plain RLM on the fixed setup described below, with a 95% interval of −3 to +9, so the difference is not clear. On the first setup both scored 0.94. We also ran held-out questions: questions whose answer documents we removed, so the right move is to decline. On the 30 both methods ran, the plain RLM declined 19 and the Jev reader 25. Asked to state a confidence, the plain RLM never said 50% or more; the Jev reader did twice, once answering from memory and once wrong.

Why an RLM, and how the numbers compare

This test uses the same setup as the Recursive Language Model paper by Zhang, Kraska and Khattab: 1,000 documents per question, too many for one prompt. An RLM gets the documents as a variable in Python, searches them with code, and sends parts to a smaller model. We chose it because it is among the strongest published methods here and its code is open, so we could run it with Sonnet 5 and add Jev to it.

What each run showed

  1. 01

    Jev tools lost the first main run.

    With a limit of 20 turns on 100 questions, the RLM with Jev tools scored 0.84 against the plain RLM's 0.94 (p = 0.002, so very unlikely to be chance) and cost $0.34 against $0.30. Each Jev call used up a turn, so it ran out of turns more often.

    Jev tools worse
  2. 02

    The Jev check lost on the main questions.

    The Jev check runs Jev decide on the documents an answer cites, to ask whether they support it. Sonnet also states its own confidence with each answer. We measured how well each score separates wrong answers from right ones with AUROC, where 1.0 is perfect and 0.5 is a coin flip. On the plain RLM's answers, the Jev check scored 0.87 and Sonnet's stated confidence 0.93.

    Stated confidence wins
  3. 03

    A one-call shortlist tool fixed part of it.

    We replaced Jev screen with a shortlist tool that screens every document and returns the top few in one call, to save turns. On the 22 questions where the RLM with Jev tools ran out of turns, this version got 13 right. The original got 7, and the plain RLM got 17.

    Partial fix
  4. 04

    Fixing the run setup closed most of the gap.

    The fix allows 30 turns and, when turns run out, tells Sonnet to stop writing code and answer. The plain RLM scored 0.91 and the RLM with Jev tools 0.90, at $0.35 and $0.42 per question. The Jev tools still added cost.

    Tie, Jev tools cost more
  5. 05

    A small trial of the Jev reader.

    On 30 random questions, the Jev reader scored 0.87 against the plain RLM's 0.90, at $0.13 against $0.33 and 19 s against 139 s. On 15 hard questions, where an RLM had run out of turns in the first setup, both scored 0.80. With only 30 questions, the interval still allowed a loss of about 17 points.

    Trial
  6. 06

    The Jev reader on all 100 questions.

    The Jev reader scored 0.94 against the plain RLM's 0.91, at $0.13 against $0.35 per question and 21 s against 143 s. The 62 questions outside the trial show the same pattern. When none of the top 8 documents is relevant, the reader says the documents cannot settle the question.

    Cheaper and faster
  7. 07

    Sonnet declines on its own when nothing supports an answer.

    Over the plain RLM's 100 answers plus 20 held-out questions, the Jev check had an AUROC of 0.910 against 0.955 for stated confidence, and the 95% interval favored stated confidence. With 30 held-out questions the AUROCs were 0.912 and 0.958. On all 30, the plain RLM declined or stated under 50% confidence, so the Jev check had little to catch.

    Stated confidence wins
  8. 08

    The Jev screen is why one call is enough.

    This check needed no API calls. BM25, a standard keyword ranking, put a document holding the answer in its top 8 on 49 of 100 questions. Jev screen did on 94. BrowseComp questions describe the answer through indirect clues, which keyword ranking misses. We did not run a reader on BM25's top 8, or an embedding retriever.

    Jev screen wins

The run setup, not Jev, caused most of the gap

The run setup is the code that drives the RLM: how many turns Sonnet gets and what happens when they run out. In the first setup, Sonnet had 20 turns, and its last message was often more code instead of an answer, which counted as no answer. The fixed setup gives 30 turns, and the last turn tells Sonnet to answer from what it has found, without code. Below are the same 100 questions on both.

  • The Jev tools still cost more, $0.42 per question against $0.35.

  • The whole study cost $208, and Jev was $18 of it, or 9%.

Limitations

  • Scale. Jev screen scores every document, so its cost grows with the number of documents. At 1,000 documents it was $0.09 of the Jev reader's $0.13 per question. At 100,000 documents it would be about $9. A larger corpus needs a cheap first search, by keywords or embeddings, to cut it to about 1,000 documents before Jev. Jev can only pick from what that search keeps, and we have not tested this at that scale.
  • An easy, small test. Each question's 1,000 documents always include its answer documents, and the rest are random. In a real corpus, many documents can look close to the answer, which would make both searching and screening harder. The sample is also small: 100 main and 30 to 50 held-out questions, one run each, scored by a Sonnet 5 judge. Rerunning moves counts by about 3.
  • No other retriever. We compared Jev screen with BM25 keyword ranking only. An embedding retriever might also put the answer documents in the top 8.
